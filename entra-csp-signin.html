Mid-October, your sign-in page stops running outside scripts.

Microsoft is starting to enforce a strict Content Security Policy on Entra ID sign-in pages mid-to-late October 2026: only Microsoft-hosted scripts will run on login.microsoftonline.com. Any browser extension or admin tool that injects code into the login page stops working — silently.

What changes — and what doesn't

  • What changes: a strict Content Security Policy on the Entra ID sign-in page. Injected code from browser extensions and third-party tools gets blocked.
  • What doesn't break: signing in. Users can still log in normally — it's the injected tooling that dies, quietly, in the background.
  • Scope: browser-based sign-ins only. MSAL and API authentication flows are unaffected.
  • Setup: none. It's on by default when it rolls out to you.

Timing, stated carefully: Microsoft's Secure Future Initiative communications put this mid-to-late October 2026, corroborated by October 2026 coverage. We're not hard-dating it — rollouts move — which is exactly why the check below matters more than the date.

What breaks, in plain English

Password-manager autofill that injects into the login page. SSO helper extensions. Admin tools that overlay the sign-in flow. Anything your staff or your IT person installed that "helps with logins" by touching the page itself. After the rollout, those tools just stop doing their thing — no error, no warning. The help-desk ticket reads "the login helper stopped working" and nobody knows why.

How to check today: open your browser's developer console on the Microsoft sign-in page and look for red Content-Security-Policy violation messages. Violations now = broken tooling later. That's the whole audit.

The honest version

This is the second mid-October deadline in the queue — the first is the October 10 EWS allow-list enforcement — and it's the quieter one, which makes it more dangerous operationally. Nobody announces "your extension stopped working." The failure mode is a slow accumulation of confused users and dead tooling. The fix is an afternoon's audit, which is why this page leads with the dev-console check instead of the date.

The enterprise line, translated: Microsoft told enterprise customers to stop shipping sign-in-page-injecting tooling. For a small shop, the translation is simpler: list what touches your login page, and assume anything on that list needs a replacement or an update.

Three actions — before the rollout

1. Inventory what touches your sign-in page

Browser extensions, SSO helpers, password-manager integrations, admin overlay tools — on every machine your staff uses to sign in. If it interacts with the Microsoft login page, write it down.

2. Run the dev-console check

Open developer tools on login.microsoftonline.com and watch for CSP violation messages in red. Each one is a tool that will silently break. Screenshot the list — that's your fix list.

3. Replace or update the injectors

For each tool on the list: check with the vendor for a version that doesn't inject into the sign-in page, or replace it with one that uses supported authentication flows (MSAL, not page injection). Do it before mid-October, not after the tickets start.
