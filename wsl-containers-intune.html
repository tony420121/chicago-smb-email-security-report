Your developers just got a new way to run unvetted software. Here's the allow list.

As of September 30, 2026, WSL containers are generally available on Windows — developers can build, run, and deploy Linux containers directly on their work laptops, no separate platform required. Microsoft shipped exactly two Intune controls with it: turn the feature on or off, and restrict image pulls to an approved-registry allow list. Two settings. Ten minutes. Here's what they do.

What shipped, in plain English

WSL (Windows Subsystem for Linux) can now run Linux containers natively — no Docker Desktop required for basic workflows. Developers get a new command-line tool, wslc.exe (with a container.exe alias for people who already know container commands), plus an API that lets native Windows apps spin up Linux containers programmatically. It installs with wsl --update or from Microsoft's GitHub releases page. VS Code dev containers can already use wslc as their default driver.

Why this is a security story, not a developer story: a container image is software, pulled from a registry — a server that hosts container images. Anyone can publish an image. A developer pulling a random image to "try something" is downloading and running unvetted code on a company laptop, inside your network. That's a supply-chain decision being made at the keyboard, and until September 30 there was no built-in way to govern it.

The two Intune settings

Microsoft shipped exactly two controls for WSL Containers in Intune. That's the whole governance surface — described here as the settings themselves, not a console walkthrough:

Setting 1: Enable or disable WSL Containers

Administrators can switch the entire feature on or off across managed devices. Don't need containers on a machine? Turn it off there.

Setting 2: Container registry allow list

Restricts image pulls to a defined set of approved registries. Microsoft's stated purpose: keep developers pulling only images that meet the organization's security and compliance requirements. This is the important one — it's the difference between "developers can run anything" and "developers can run what we approved."

Visibility
Microsoft Defender for Endpoint's WSL plugin now also covers container activity — it can surface process, file, and network activity from inside a container and connect it back to the Windows host, so investigators don't need a separate workflow.

The 10-minute check — do this today

1. Decide who needs it

Developers on Windows laptops: yes, probably. Everyone else: no. Write the list down — it should be short.

2. Set the allow list first

Have your admin define the approved-registry allow list — one of the two controls Intune ships for WSL Containers (the other is the feature on/off switch). Start with your company's private registry plus Docker Hub's official images if you must — then narrow it.

3. Disable it where it's not needed

For every managed device not on your list from step 1, the feature stays off. Default-deny, exceptions documented.

4. Confirm Defender coverage

Verify Defender for Endpoint's WSL plugin is active on the machines where containers are allowed — that's your visibility into what the containers actually do.

5. Tell your developers

Thirty seconds: "Container images now come from the approved list. If you need one that isn't on it, ask — don't work around it." Shadow workarounds are how unvetted images get in.

The honest version

This is endpoint hygiene, not email security — it's the narrowest-audience page in the funnel, and it only matters if you have developers on Windows laptops. If that's not your shop, skip it without guilt.

But if it is: ungoverned software installation is how supply-chain compromises start, and September 2026 already showed what trusted-tool abuse looks like at scale. Two settings is the cheapest insurance this funnel has ever offered.
